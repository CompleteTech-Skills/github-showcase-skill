# Content module (`showcase.py content`)

Repository content checks that the estate audit assigned to the skill: links (CQ-04, RP-09), the language bar (RP-07, CQ-08), Actions health and merge side effects (RP-06, RP-01, CQ-13), README images (RP-03, RP-10), the About sidebar (RP-05), repository icons (RT-04, decision 12) and the social preview (R10). Like every other module it is **read-only toward GitHub**: nothing here rewrites a README, edits `.gitattributes`, touches a workflow file or uploads anything. Each action reports facts and emits proposals: unified diffs, `gh` argv and `scripts/writer.py` jobs (`browser` jobs for UI-only steps, with the exact click path in `steps`).

## Commands

R10 includes the personal-profile capstone (decision 20). Social upload jobs and `doctor` use the same applicability rule. For archived polishing, re-capture metadata inside the approved unarchive window before planning the social job; an archived capture does not authorize an upload.

Run from inside the target checkout, or pass the global `--repo-dir DIR` and `--meta FILE` like the repository commands.

```bash
S=<skill-dir>/scripts/showcase.py
python3 $S --meta meta.json content social [--out assets/social-preview.png] [--job]          # alias of social-preview
python3 $S --meta meta.json content icon prompt [--glyph glyph.yaml] [--option A|B] [--out art/prompts/ORG/REPO/icon.md]
python3 $S --meta meta.json content icon normalize --in candidate.png [--ground auto|transparent|keep] [--ground-tolerance DE] [--out assets/icon.png] [--preview icon-48.png]
python3 $S --meta meta.json content icon check [--out assets/icon.png]
python3 $S content links [FILE ...] [--base-ref origin/main] [--online [--cache links.json]] [--strict] [--diff]
python3 $S --meta meta.json content linguist [--min-share 0.02] [--language Python]
python3 $S --meta meta.json content actions [--runs runs.json] [--workflows workflows.json] [--pages pages.json] [--approval WORKFLOW=ID]
python3 $S content images [FILE ...] [--base-ref HEAD] [--approval-id ID] [--out-dir candidates/] [--online]
python3 $S content sidebar --facts facts.json [--packages packages.json]... [--current states.json] [--repo OWNER/REPO]
```

Every action also takes `--report FILE` (the JSON result), `--jobs FILE` (append the writer jobs as JSON lines), and `--registry`, `--approved`, `--approved-yaml`, `--actions` for the shared org resolver.

### Icon ground rule (`icon normalize`, `--ground auto`)

- Transparent corners: keyed as is. Four opaque corners closer than `--ground-tolerance` dE to each other (default 3.0; a finite number >= 0; identical corners always count as one ground at 0) are one ground: a dark one (relative luminance < 0.2) that is not within dE 12 of the card colour is kept full-bleed as a night tile (unless the kept PNG would exceed 300 KB, then it is keyed: `auto_reason` budget-fallback); any other uniform ground, pale or card-coloured, is keyed to transparent (the PNG stays under 300 KB).
- A slightly vignetted ground with corner dE above 3.0 fails with `icon-ground` and a message naming the measured dE and `--ground-tolerance`; rerun with e.g. `--ground-tolerance 5` for corner dE 3.1-4.9. Larger spreads still fail, so ask for a flat ground (the option A prompt states the exact `card_fill` hex with no vignette, texture, gradient, shadow or glow).
- A raised `--ground-tolerance` widens the key threshold only above the default 3.0 (explicit modes stay byte-identical at the default), and a kept night tile with such a vignette is flattened to one ground so `content icon check` passes it. The flatten is feathered: pixels within the corner spread of the ground become the flat ground, and a soft ramp of 6 dE blends back to the original, so a smooth glow or bloom around the glyph stays smooth (no hard ring) while the glyph edge stays hard. The transparent key uses a soft 3 dE alpha ramp only when --ground-tolerance is raised above 3.0; at the default the key stays the original 0/255 step.
- `--ground keep|transparent` behave as before; `--ground-tolerance` also sets how alike the corners must be for them.

## Results and exit codes

Each action prints one JSON object (`command: "content"`, `action`, `owner`, `repo`, `result`, `logs`, plus its facts, `proposals` and `jobs`). `result` is `pass`, `warn`, `proposal`, `fail`, `needs-writer`, `needs-input` (a capture such as `--runs` is missing; the facts it could check are still reported) or `exempt`. `fail` and `needs-writer` exit 1, a refused owner or a usage error exits 2, and a missing required input (no art direction, no registry row for the org, or `links`/`images` run where there is no README or Markdown file to check) exits 4. Only watching-org forks (`exempt:watching-fork`) and a placeholder org's `.github` (`exempt:placeholder-org`) are `exempt` from icons, and a watching-org repository that is neither a fork nor `.github` is held (`hold:watching-non-fork`, exit 2 unless `--allow-hold`) until decided; the watching org's `.github` needs its own icon. This is the same applicability the banner, card, `lint all` and `doctor` use (decision 12); forks outside the watching org, backups and `.github` repositories need their own icon; excluded, HOLD and T3 owners are refused under any of their logins (the shared resolver, CQ-03), and a family on hold (`brand.yaml` style `hold`) is refused unless `--allow-hold` is passed, as `banner` and `card` refuse it.

## Network

None by default. `links --online` and `images --online` make cached, rate-limited HEAD/GET requests to the hosts the files link to and read-only `gh api` GETs; `--cache` is the only state they keep. Local, private-network and `example.*` hosts are allowlisted and never fetched.

`--strict` (on `icon check` and `icon normalize`, also set by the family key `icon_strict_family_ink: true` in `references/brand.yaml`, which is off by default) makes the family-ink check fail instead of warn when the icon's dominant ink is not a family ink. Without the flag it stays a warning and the exit code is unchanged. With no family palette (`icon_ink` and `icon_spark` absent) the family-ink check is not emitted, so `--strict` has no effect there and `needs-input:icon-palette` is still logged.

`--min-contrast` sets the contrast floor of the icon's dominant ink on the card plate (on `icon normalize` and `icon check`). The precedence is the CLI flag, then the family key `icon_min_contrast` in `references/brand.yaml`, then the default 3.0. The default stays 3:1 because a higher floor would change results that already pass. The recommended floor for the card plate is 4.5:1 (WCAG AA body text); set it with `--min-contrast 4.5` or `icon_min_contrast: 4.5` for a family. The valid range is 1 to 21; any other value, or a non-number, is a usage error (exit 2). A failing contrast check fails the icon (exit 1), as the other failing icon checks do.

`--ocr` (on `icon check` and `icon normalize`, off by default) adds an optional text check: when `tesseract` is on `PATH`, the icon is composited on the configured family card colour (card_fill) and read with it, and words of 2 or more alphanumeric characters count as text. Found text warns (`no-text`, detail `OCR found text: ...`) and fails the icon with `--strict`; no text passes. Single characters and punctuation are ignored. Without `--ocr`, or without `tesseract`, nothing changes: `no-text` stays a manual review, and an absent tool logs `needs-input:ocr-unavailable` without changing the result or the exit code (a tool that fails to run logs `needs-input:ocr-failed`). The tool is never installed by this package. An unreadable or undecodable PNG (bad structure, or valid structure with corrupt compressed data) fails the `png` check, and with `--ocr` still returns `logs` as `[]`. On `icon normalize`, an unreadable or undecodable `--in` candidate also fails the `png` check (exit 1, `art-fail:icon-qa`, `out` null, nothing written), while a missing `--in` file stays a usage error (exit 2). The 48 px set sheet stays manual.

## Without the estate bundle

For an older custom `--config` that omits `icon_ink` or `icon_spark`, normalization
and checking still run their other QA checks, with `needs-input:icon-palette` in
the logs and no family-ink comparison. The bundled option A glyph prompt needs
both tokens and exits 4 with their names; add them to the custom config or pass an explicit
`--art-direction FILE` with a family palette. The shipped config supplies both
tokens for every family. Option B uses the illustration palette and does not
require these glyph tokens, whether art direction is selected implicitly or explicitly.

All actions run on a checkout and a metadata file alone. The registry and approvals refine the result when present (a renamed org's packages and links resolve to its current login; a registry `language:` override reaches the chip); without them the resolver uses `references/brand.yaml` and treats nothing as approved. `icon prompt`, `icon normalize` and `icon check` default to the skill's bundled [art-direction.md](art-direction.md), regardless of the working directory. Option A uses its repository glyph template and the family's `brand.yaml` tokens; option B uses its illustration template. Pass `--art-direction FILE` to select an explicit art direction file (relative paths resolve from the current directory), including an estate-format file with `(b) Family palette` and `(d) Shared prompt template` sections. A missing selected file reports `needs-input:art-direction` and names that path; `prompt` exits 4, while normalization and QA log the missing palette and continue their other checks.
