# Org module (`showcase.py org`)

Decisions 5 (one home, `also_in` cross-listing), 8 (complete org About), 14 (pins and star Lists), 15 (profile README kit), 18 (footer), 21 (dark designs) and 23 (organizations), applied to STANDARD §1.4 (the O-checks), §2.3, §6, §8.1 and §8.2. The module is **read-only toward GitHub**: it renders the org profile README from the registry's public slice and prints JSON plans, `gh` argv and `scripts/writer.py` jobs. The orchestrator's writer queue (or, used standalone, the user) applies them; UI-only steps are `browser` jobs with exact click paths. The org About field table, the `.github` file table and the profile structure are in [orgs-and-projects.md](orgs-and-projects.md) and [profile-readmes.md](profile-readmes.md).

## Commands

```bash
S=<skill-dir>/scripts/showcase.py
python3 $S org about   ORG [--email-approved]                       # O2: PATCH orgs/ORG payload, verified-domain check
python3 $S org profile ORG --meta-dir META [--out-dir DOTGITHUB] [--render] [--lists star_lists.json]
python3 $S org pins    ORG [--lists star_lists.json] [--repo-ids ids.json]   # O6: browser pin jobs + the star List plan
python3 $S org labels  ORG --meta-dir META                          # §6.3 rename-before-create jobs for every repo of the org
python3 $S org health  ORG [--dot-github CHECKOUT]                  # O4: §8.1 default files of ORG/.github
python3 $S org doctor  ORG --snapshot org-snapshot.json [--dot-github CHECKOUT] [--avatar avatar.png] [--doctor-format tsv|json|md] [--header]
```

Every action takes `ORG` (any former login resolves, see below), `--registry`, `--meta-dir`, `--decisions`, `--approved`, `--approved-yaml`, `--actions`, `--allow-t3` and `--jobs FILE` (append the writer jobs as JSON lines).

## Inputs, with or without the estate bundle

| Input | Default | Without the bundle |
|---|---|---|
| Registry (`registry/estate.yaml`) | the bundle beside the skill, or `$SHOWCASE_ESTATE_ROOT/registry/estate.yaml` | `--registry FILE`; `org` exits 4 (`needs-input:registry`) without one. Layout: `version`, `profile`, `orgs.<login>` with `tier`, `profile`, `final_repos`, `pins_public`, `pins_members`, `sections`, `also_in_outgoing`, `also_in_incoming`, `favorites`, `star_list`, optional `former_slugs`, and top-level `placeholders` |
| Repository metadata | none | `--meta-dir DIR`: one JSON per repository (`meta` output, `gh api repos/O/R`, or the scratch capture), read recursively, so pass the top folder (`state/meta`) and repositories still filed under the owner an approved transfer moves them from are found; the `.github` entry may carry `files` for `health` and the profile's re-template gate, either as the fixtures' map `{path: {bytes, head} | true | null | false}` or as the sorted path list `meta --from-gh` writes (the recursive tree of the default branch: a listed path is present; an unlisted one is absent only when the capture records `files_complete: true`, i.e. GitHub did not truncate the tree, and unknown otherwise; a list carries no README text, so `banner: keep-existing` then needs `--banner`); `last_substantive_commit` comes from `meta --from-gh` |
| Exposure flags | `decisions/decisions.json` | `--decisions FILE`; flagged repositories (`secrets-risk`, `exposure`, `pii`, `private-lan`, ...) never enter the public slice |
| Approvals | `decisions/approved.tsv`, `decisions/APPROVED_ACTIONS.yaml`, `decisions/estate-actions.json` | `--approved`, `--approved-yaml`, `--actions`; missing files mean "nothing approved" |

The synthetic `examples/estate/` tree runs every action offline: `SHOWCASE_ESTATE_ROOT=examples/estate python3 scripts/showcase.py org profile Northwind-Trading-Co --meta-dir examples/estate/meta`.

**The registry is private data.** It names private repositories, members-only pins and internal notes. Read it; never copy it, or any part of it other than the public slice, into a repository. `org profile` renders only the public slice (public, non-HOLD, non-exposure repositories; no `pins_members`, no `why` or `notes` text) and fails (exit 1, nothing written) when the README or `data.json` names a private slug, a members-only pin or a sentence from an internal note. A `favorites` entry owned by an estate org (any login the resolver knows from the registry or `brand.yaml`, the steward account, a registry placeholder or merge-source org, or an excluded, HOLD, T3 or watching owner), and any favorite whose metadata was captured, passes the same public-slice test: a private, HOLD, excluded-owner or exposure one is dropped and logged `favorite-dropped:private-or-unknown` (never named), and an estate one with no metadata is left out and logged `needs-input:favorite-visibility:OWNER/REPO` (result `incomplete`, as for any repository of unknown visibility, until its metadata is captured); only favorites outside the estate with no captured metadata (other people's public projects) are listed as given. The org's star List (`org pins`) takes its items from the same rule, so it never adds a favorite the profile would not name. The leak check's private set covers every captured repository, in any org and whoever the owner, whose metadata says it is not public, as well as the dropped favorites.

## Org logins after renames (CQ-03)

Every org lookup in `org`, `project` and `content` goes through one resolver (`scripts/ctshowcase/resolver.py`), so an approved rename never breaks a brand row, a registry key, the watching-org exemption or a refusal. It reads, in order:

1. `former_slugs: [old, ...]` on an org row in `references/brand.yaml` or the registry;
2. the registry's `placeholders:` (`login`, `successor`) for orgs the user creates at freed logins;
3. approved `org-rename` and `org-merge` items (`approved.tsv`, `APPROVED_ACTIONS.yaml` with `approved: true`, joined with `estate-actions.json`).

**Repository slugs.** The registry writes every repository under its final slug, after its `rename` or `transfer` in `estate-actions.json`. Until that action runs, the metadata (and GitHub) still has the old slug, so the resolver maps final slug to today's slug: a rename inside the org always resolves (the repository is homed there either way), a transfer from another org only once it is approved. Profiles, label jobs and pins then use today's slug (GitHub redirects it after the rename), log `repo-alias:<final>-><today>:<action>` or `pin-current-slug:<today>:<action>`, and the leak check guards a private repository under both slugs. Regenerate after Phase 2 so the profile names the final slugs.

A rename moves the org (`CompleTetech-Security` becomes `CompleteTech-Security` once `org-001` is approved), so jobs, URLs and links name the new login while the old one still finds the row. A merge keeps the old org as a placeholder that points at its successor. Until a rename is approved, the current login is the old one. After an approved rename, add the old login to the org's `former_slugs` in `brand.yaml` before any write in that org (ORCHESTRATOR Phase 1.1).

## Writer jobs

Every job has `{id, phase, kind, repo|org, approval_id?, argv, note}`; `browser` jobs carry `url`, `ui_action` and exact `steps` (ending with a screenshot path and the Danger Zone safety step) instead of `argv`. Ids are stable, so re-submitting a plan is a no-op in `scripts/writer.py`. The skill never runs a job.

| Phase | Action | Kind |
|---|---|---|
| 1.2 | `about` | `org-about` (`gh api -X PATCH orgs/ORG ...`; the email only after review q26 approves it) |
| 3.2 | `labels` | `labels` (`gh label edit` or `gh label create ... -R ORG/REPO`) |
| 6.2 | `pins` | `browser` (`org-pin`, `org-pin-order`); star List GraphQL mutations inline |
| 6.5 | `labels` | `browser` (`org-repository-defaults`: Settings → Repository → labels and default branch `main`) |

## Refusals and logs

Excluded owners and T3 orgs without `--allow-t3` (co-owner sign-off) exit 2 in every action; HOLD orgs exit 2 in `profile` and `labels`, while `about`, `pins`, `health` and `doctor` still report. `labels` answers `n/a` for T2-R, T3 and romgenie orgs. Placeholder orgs return `user-step`. A repository with no metadata (`--meta-dir` missing or incomplete, or a capture that failed) is left out of the profile as possibly private (`needs-input:visibility:<repo>`, result `incomplete`); one the registry homes here only after an unapproved transfer from another org is not here yet and is logged `pending-move:<repo>:<action id>` instead; when no repository is known to be public, `profile` exits 4 (`needs-input:metadata`) instead of rendering the private-org variant, which would be false. Every profile, the watching org's included (its `footer: false` exempts only its upstream forks), ends with the link row and the decision 18 footer. Common logs: `needs-input:registry`, `needs-input:org`, `needs-approval:profile-retemplate` (an existing profile is re-templated only when approved, §8.2; with `--out-dir` nothing is written), `repo-alias:<final>-><today>:<action>`, `pin-current-slug:<today>:<action>`, `needs-approval:org-email`, `email-blank`, `needs-input:star-lists-capture`, `needs-input:favorite-visibility:OWNER/REPO`, `favorite-dropped:private-or-unknown`, `needs-input:label-references`, `needs-input:dot-github-files`, `needs-approval:create-repo:.github`, `recency:pushed_at` (no `last_substantive_commit` yet, so flagship order falls back to `pushed_at`).

## Never

- Never compose an org name or description: values come from the registry and the identity table.
- Never call `PATCH /user` from the skill. The personal profile is redone in its entirety as the Phase 8 capstone (decisions 9 and 20: About, avatar, public org memberships, contribution settings, profile README and repository, pins, star Lists, gist review). Its About fields follow review q92: the browser by default (Settings → Public profile, screenshots before and after); `PATCH user` only as a writer job under an approved `user-about` row, after `snapshot.py --user CompleteDotTech`; social links only through `POST /user/social_accounts` (add only, at most 4).
- Never pin before everything else in the org is final; pins are browser steps.
- Never create `.github-private`, and never list a private repository on a public profile.
- Never commit a public file the run wrote without `showcase.py lint public-leak FILE... --meta-dir DIR`: the same leak check `profile` runs, against every registry org's private set (or `--org ORG[,ORG]`); without metadata every repository counts as private, so it fails closed.
