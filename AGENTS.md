# CompleteTech LLC Skills: maintainer instructions

Read [SKILL.md](SKILL.md) for specialist behavior, [ONBOARDING.md](ONBOARDING.md) for first use, [BRANDING.md](BRANDING.md) for presentation and handoffs, and [CONTRIBUTING.md](CONTRIBUTING.md) before changing this checkout.

Preserve the activation key, existing CLI paths, templates, dependencies, approval gates and consent boundaries. A common package does not require identical generators. Keep private assets private and use synthetic fixtures. Never scan personal logs, submit certificate data, install schedules, send messages or publish artifacts merely to test alignment.

Run `python -m unittest discover -s tests -p 'test_package_*.py' -v` and `python scripts/validate_package.py`, then the existing Quality checks. Do not disable failing checks or replace verified evidence with successful rendering. Describe any checks not run.

Shared files are maintained together through the orchestrator's catalog and drift audit. Update affected siblings in focused PRs; review exact heads and checks before merging. Registry publishing and visibility changes are separate actions. Never claim a PR exists or merged without its successful GitHub response.

Run every generation, check and plan through `scripts/showcase.py`; never hand-edit generated banners, cards, profile READMEs or marker blocks. Brand data lives only in `references/brand.yaml`. Never commit private-repo metadata to fixtures or examples. The Quality checks here are `python -m pytest -q` and `python scripts/validate_quality.py`; `scripts/validate_package.py` and `tests/test_package_contract.py` are the family's shared files and stay byte-identical to the siblings' (package-specific checks belong in `validate_quality.py`).

The skill is read-only toward GitHub. It proposes descriptions, topics, labels and README changes as diffs, `gh` command lines and change records; the orchestrator's single writer queue performs every write. The composite Action in `action.yml` is the one component that commits, and only into the repository it runs in. Dark designs are the estate standard (decision 21): never add a light variant or a `-dark`/`-light` sibling file; the decision 18 footer is the only `<picture>`. See [references/decisions.md](references/decisions.md) before changing any rule that a decision settled.

The `org`, `project`, `enterprise` and `content` command groups are a fixed contract that the orchestrator and other workstreams call by name (`org {profile,about,pins,labels,health,doctor}`, `project {capture-query,normalize,copy-plan,readme,lint,estate-plan}`, `enterprise {snapshot-query,doctor,plan}` beside the original `discover`, `snapshot`, `seat-check` and `diff`, `content {social,icon,links,linguist,actions,images,sidebar}`, where `content social` is the social preview's contract name and the top-level `social-preview` stays only as a hidden, deprecated alias; `org-banner` and `org-tile` stay top-level generators): keep those names and every existing command working. Each module registers its own parser (`register(sub)`) and is wired in `scripts/showcase.py`. Planned GitHub changes leave only as `scripts/writer.py` jobs `{id, phase, kind, repo|org, approval_id?, argv, note}` (UI-only steps as `kind: "browser"` with exact `steps`), with every mutation inline. Every org lookup goes through `scripts/ctshowcase/resolver.py`, never a bare string comparison, so renamed orgs keep resolving (CQ-03). The estate registry is private: read it, never copy it into a fixture, example or repository; synthetic stand-ins live in `examples/estate/` and `tests/fixtures/`.
