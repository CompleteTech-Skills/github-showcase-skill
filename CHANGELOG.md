# Changelog

All notable changes to `github-showcase-skill` are recorded here. Versions follow [Semantic Versioning](https://semver.org/): a new major version changes a generated surface, a command's contract or the standard version (`ct-std-v1`); a minor version adds a command or option; a patch fixes output without changing the contract. The template's workflow pins a release tag by its commit SHA, so every entry below names one tag.

## Unreleased

### Added

- `org labels ORG --repos-from-gh` plans labels across accessible repositories without the private estate registry, with paginated read-only GitHub capture, optional verified local checkouts, unchanged reference guards, and a documented org-default-forms-first workflow. Registry-backed plans still require the org registry row, and checkout repository names match GitHub case-insensitively, including resolved pending renames. Registry-free runs also isolate lazy brand lookups from estate decision files, and held reference rewrites retain their file/line guidance with an incomplete result. Workflow/labeler/release/Renovate references remain final skips rather than unresolved input requests. Missing Windows device-named checkouts fall back to captured metadata instead of aborting the org plan. Pending transfers check the repository's current owner's default issue forms and hold renames when that evidence is unavailable. Sparse or partially missing checkouts retain reference holds based on captured paths and the Git index, while unrelated omitted files remain allowed.
- Global `--allow-t3` (before the command) signs off a T3 co-owned repository for one invocation across every repository command, generator, `lint` and the `org` and `project` groups, not only `meta`. The default still refuses T3 owners (exit 2, `t3-signoff`), except repository `doctor` (always admits them; R7 is `hold` only without the flag), local `meta` normalization and `fingerprint`, which do not check eligibility; excluded and HOLD owners stay refused. Pick Your AI also gets its own palette, mark and attribution (PR #20).

### Fixed

- Windows contributor tests now use explicit UTF-8, native path basenames, a platform-independent read-only metadata stub, and Git Bash with stdin-safe Action scripts. All 15 issue #9 failures are individually documented; the full suite now runs in Windows, Linux and macOS CI.
- Lint accepts file operands after options on older Python 3.12 versions while continuing to reject unrecognized options.
- The Action's optional render arguments support macOS Bash 3.2, including an empty argument array with `set -u`.

- `org health` and `org doctor` run available checkout/snapshot checks without the private estate registry, retaining missing-org errors when a registry is supplied or discovered. Doctor combines available file and visibility evidence without inventing completeness or dropping explicit absence, normalizes REST/GraphQL privacy fields, distinguishes absent fields from explicitly cleared identity fields, checks private links under known renamed repository/owner paths and supported verification reason codes, and reports incomplete registry-dependent coverage instead of aborting or claiming the org is done.
- Older valid custom brand configs without the optional icon palette tokens retain icon normalization, checking and option B illustration prompts; missing palette inputs are reported without a traceback, and the bundled option A glyph prompt explains which tokens to add or how to supply an explicit palette.
- `content icon` uses the bundled `references/art-direction.md` in every working directory. The option A glyph template uses dedicated, contrasting `icon_ink` and `icon_spark` brand tokens and the documented family seed (or the tool's default when absent) without requiring private estate files; explicit art-direction overrides remain supported and missing paths are named in the error.
- CLI stdout and stderr are configured as UTF-8 before argument parsing, preserving their existing error handlers, so redirected Windows output preserves Unicode in label plans, raw footer markup, help and diagnostics without `UnicodeEncodeError`, and undecodable filenames still use the stream's original escape policy.
- The Action summary and quality validator decode CLI results explicitly as UTF-8, preserving non-ASCII descriptions on Windows rather than corrupting them or failing with `UnicodeDecodeError`.

- `doctor` reports disabled-Issues label checks, inapplicable social previews and archived community health as `n/a`, while preserving label coverage during approved archived polishing and unknown captured values on applicable surfaces. Social upload plans share the R10 applicability rule and include the personal-profile capstone.
- `doctor` reports R11 as `n/a` for archived repositories and outside T1/T2 organizations (personal-account, utility and co-owned repositories), matching the definition of done.
- R5 preserves upstream defaults on forks (forks in the watching and archive orgs still need Issues off, as `adopt` plans) and accepts a captured user keep decision for other default branches without relaxing the merge or Issues checks. `adopt` and the `doctor --estate` proposals honour the same keep decision: `adopt` logs `default-branch kept (user)` instead of asking for a `rename-default-branch` proposal, and neither asks for one on a fork.
- One fork rule (GitHub's fork flag or a `-fork` slug, whatever type a repo config sets, plus a detected `fork` type) is shared by `doctor` (R5, R6, R10, R11), `adopt`, `labels --plan`, `org labels`, the `doctor --estate` proposals, the social preview, the card exemption (in `card`, `lint all`, `doctor` and the org and personal profile pages, under every owner code) and the watching-org exemptions, so a repository is never a fork to only some of them for what applies to it. Content (the README variant, the description template and the `fork` topic) still follows the detected type, which a repo config may set. R1 exempts GitHub forks only, as the estate proposals do: a non-network copy follows `UPSTREAM-fork` naming (§3.1).
- `content social` renders the personal-profile capstone and backup repositories wherever R10 and the `adopt` upload job include them; it previously exempted them, so the planned upload had no image. Where R10 leaves them out (the archive org, an archived capture) they stay exempt.
- Label job plans include a per-repository `labels:OWNER/REPO` group for writer reconciliation. Explicit orchestrator groups are preserved.
- `adopt` withholds jobs and change records for an archived capture, with instructions to re-capture inside the approved unarchive/polish/re-archive cycle. Security jobs are emitted only for active eligible repositories.

## 1.0.0 — 2026-10-26

First public release, for the CompleteTech GitHub estate standard `ct-std-v1`.

### Added

- Repository surfaces: README hero banner (1280×360 and 2560×720), repo card SVG, social preview (1280×640), repo icon (1024×1024), the estate footer and README marker blocks for every README variant.
- Checks: `describe`, `topics`, `labels --plan`, `readme` scaffold and upgrade, `lint` (SVG, banner, PNG, README, public leak) and `doctor` (R1 to R11 plus the art columns).
- Command groups: `org` (profile README, About, pins, labels, health, doctor), `project` (capture, normalize, lint, copy plan, README, Estate board), `enterprise` (discover, snapshot, plans, doctor) and `content` (sidebar, links, images, art direction).
- `meta --from-gh` records `last_substantive_commit` (CQ-16) and takes `--allow-t3` after co-owner sign-off.
- The composite Action (`action.yml`) that the repository template runs to bootstrap and refresh its own README and images.

### Security

- Read-only toward GitHub: every write is printed as a `gh` argv or a writer job for the estate's writer to run.
- `org profile` lists an estate-owned favorite (placeholder, merge-source and excluded owners included), or any favorite whose metadata was captured, only when it passes the public-slice test, and its leak check covers every captured repository whose metadata is not public, whoever the owner.
- `labels --plan` and `adopt` hold a rename (`label-rewrite-first`) while an issue form's or `dependabot.yml`'s `labels:` entry still assigns the old label, so no rename leaves a form naming a missing label.
- A label rename is never planned without its reference check: with no checkout (`labels --plan` without `--repo-dir`, `adopt`, `org labels`), it is planned only when the captured file tree, recorded whole (`files_complete: true`: `meta --from-gh` keeps GitHub's `truncated` answer), proves no issue form, `dependabot.yml`, workflow, `release.yml`, `labeler.yml` or `renovate.json` exists; otherwise it is held as `needs-input:label-references` with the files to check.
- The label reference check also reads the owner's `.github` default issue forms for a repository without forms of its own (`org labels` from `--meta-dir`; `labels` and `adopt` take `--org-defaults` with a checkout or its metadata JSON), and parses forms, front matter and `dependabot.yml` as YAML, so multi-line values, quoted keys, aliases and a byte order mark are recognised and a file that does not parse holds the rename.
- `org pins` adds to the public star List only the favorites the public slice may name: private, HOLD, excluded-owner and exposure favorites are dropped (`favorite-dropped:private-or-unknown`, unnamed) and unknown visibility leaves the plan `incomplete`.
- `content icon` refuses a family on hold unless `--allow-hold` is passed, as `banner` and `card` do.
- `org` exposure flags match their marker anywhere in the flag (`private-keep-private`, `...-must-stay-private`, `do-not-publish`, `possible-pii-in-output`, `lan-device-inventory`, ...) and follow a repository through its move or rename (`target_owner`, `new_name`), so a flagged repository re-captured under its new slug stays out of the public slice.
- `lint public-leak` and the profile leak checks catch a private repository named under a former org login, and treat the registry's top-level `notes` and `judge_changes` and the personal profile's internal keys (`notes`, `romgenie`, pin `why`) as internal notes.
- A T3 org's repository is left out of the personal pins and more projects, other orgs' cross-listings, favorites and star List items until co-owner sign-off (`--allow-t3`), logged `t3-signoff:OWNER/REPO`.
- `project copy-plan` and the standalone `project readme` name no repository in the README of a board that is public (as captured, approved or not) or may go public (an approved visibility item), logged `readme-links:repositories-omitted (the board may go public)`; a board captured public without approval logs `visibility:public (no approval)`, not `visibility:private`.
- `labels --plan` and `adopt` refuse an `--org-defaults` metadata JSON or checkout of another org's `.github` (usage, exit 2), with the owner read from `owner`, `owner.login`, `full_name` or the checkout's own `origin` and resolved through the run's org resolver (`--config` included). A JSON without an owner, or a checkout without a GitHub origin, can no longer prove that no default issue form names a label, so the rename stays held (`needs-input:label-references`). Before, another org's `.github` was accepted and the rename was planned while the owner's default forms still assigned the old label.
- `readme --mode upgrade` (and the bootstrap `edited` path and the preserve list) replace an unmarked or drifted footer at the end of the README with the decision 18 footer instead of appending a second one. Only a block whose every line is a footer line (centring, complete.tech links, the footer's own logo image, the "Built by" credit line) is replaced; an image counts as the footer's logo only when its src or srcset is the brand footer logo URL (or the same file on another branch, with a query, or in its github.com blob/raw form) or its alt is exactly the company, never because its file name contains "logo". A centred block with an authored line (a sponsor or partner image, a thanks line) is kept, so no authored line is dropped. `lint readme` fails `D18 footer fail:duplicate`, and `footer --check` (and doctor's footer column) `fail:duplicate`, when a footer-like block outside code sits before the last block.

### Fixed

- `project copy-plan`: a view filter on a quoted Workstream value (`workstream:"Research"`) now follows the option rename, renames apply in one pass, and the template and the Estate never get the public-visibility job even with an approval row.
- `topics`: the CVE-check vendor topic and the TouchedByAnAgent domain vocabulary match the owner through the shared resolver (CQ-03), so an approved org rename (`CompleTetech-Security` to `CompleteTech-Security`) no longer proposes removing a checker's vendor topic or logs `needs-input:domain-topic` and `topics-short`.
- `meta`: normalizing a `--meta` file no longer drops keys later checks read. The social preview flag `uses_custom_og_image` (or the captured GraphQL `usesCustomOpenGraphImage`) now reaches the doctor's R10 cell, so a verified repository can be marked done; only a boolean counts, and two spellings that disagree leave R10 `unknown`. `has_pages`, `size` and the About sidebar counts (`releases`, `deployments`, `packages`, `environments`) are kept too, for `adopt`, the sidebar job and the `doctor --estate` empty-repository rule; `references/meta.schema.json` lists every preserved key.
- `content links`: a link is proposed as "this repository under a former owner" (`moved`) only when an approved repository `rename` or `transfer` action in `decisions/estate-actions.json` records the move of exactly this repository, matched under the old owner and the old name. A same-named repository in another org is a different repository, so `CompleteTech-Skills/.github` no longer proposes rewriting the decision 18 footer's `CompleteTech-LLC/.github` logo URLs. Every URL `references/brand.yaml` holds (the footer's href and logos, the brand and hub sites) is fixed content: no org-rename, transfer or online `full_name` answer rewrites it.
- `labels --plan`, `adopt` and `org labels`: rule 0 reads every Renovate config file Renovate itself reads (`renovate.json5`, `.github/renovate.json5`, `.gitlab/`, `.gitea/` and `.forgejo/` `renovate.json(5)`, `.renovaterc`, `.renovaterc.json`, `.renovaterc.json5`, and the `renovate` key of the root `package.json` on a checkout), not only `renovate.json` and `.github/renovate.json`, so a label named there blocks the rename (`label-referenced`), and without a checkout each of those files must be proven absent from the captured tree or the rename is held (`needs-input:label-references`).
- `org pins`: each favorite's star List job carries every estate org's captured star List that takes it, so two orgs sharing a favorite never remove it from each other's List; no item job is planned from a capture whose List `items` page is cut short (`needs-input:star-lists-items-paged`); a pin behind an approved move that has not run is held (`pin-gated:<repo>:<action>`) and left out of the pin-order job; a HOLD org's pins only report (`pins:hold`).
- `project copy-plan` stage 2 (and `estate-plan`) refuses a `--copied` capture that is not a board of the target (exit 2), gives each repository link a distinct job id (`order_ledger` and `order.ledger`) and refuses a plan that would reuse an id, and a Workstream option rename changes only `workstream:` and `-workstream:` filter values, never a label or other predicate with the same text.
- `project copy-plan`: the short description and README job id ends in a hash of its argv, so the README-bearing re-plan after the view jobs ran never reuses an id with other content (the writer refuses such a batch whole). The first status update (`createProjectV2StatusUpdate`, not idempotent) is planned only when the capture shows no status update (`status-update:exists` otherwise) and the Shipped view's number is known; while the plan still creates the Shipped view it is left for the re-plan (`status-update:shipped-view-pending` and a pending entry), so it is planned once and never first with a placeholder body. Its dates are the current quarter's start and end, not today, and its id ends in a hash of the whole mutation, so a re-plan within the quarter is byte-identical (the writer skips it as already queued) and one id never carries two contents.
- `adopt` and `org labels` hold a repository whose labels were not captured (`needs-input:labels`) instead of planning every standard label as a create, `labels --jobs`, `--records` and `--gh` (not only `--plan`) read the live labels first when the metadata has none, and fail with `needs-input:gh` (exit 4, nothing appended) when they cannot, and `adopt` keeps the AI-Ascension label exemption under any spelling of the owner (resolver identity, CQ-03).
- `content icon prompt --option B` finds the family addition (trademark negatives such as the TCG one) under any login of the org or its display name, so it survives a brand.yaml row re-keyed after an approved org rename (`completetech-tcg` added). It refuses with `needs-input:family-additions` when the art direction lacks that org's addition. The ART_OWNER palette lookup follows the org's aliases too.
- `content sidebar` reads a GraphQL `totalCount` (and the REST `total_count`) before any `nodes` list, so `{totalCount: 12, nodes: []}` no longer unchecks Releases.
- `content images --out-dir` no longer writes a one-frame lossless candidate for an animated PNG. Its check reads `animated: N frames` and no candidate is offered.
- README marker blocks, `<!-- showcase:license -->` and the template-body block shown inside fenced (``` or ~~~) or inline code are examples and are never regenerated by `readme --mode header`, `upgrade` or `--bootstrap`; on the bootstrap `edited` path only the real block's pristine marker is dropped, never one shown as an example. A line that starts with three backticks but has another backtick later (```` ```npm test``` runs ````) is inline code, as in CommonMark, not a fence opener, so it no longer hides every marker, H1 or link after it from `readme`, `lint readme` and `content links`.
- `readme`, `lint readme` and the repository context (preserve list, own-banner check) drop a leading UTF-8 byte order mark, so the old H1 of a BOM README is folded into the header instead of being kept as a second H1.
- shields.io badge segments are percent-encoded after the `-`/`_` doubling (`language-C%23-1E3A8A`), so `#`, `?`, `/` and `%` no longer cut the badge URL.
- `lint readme` ignores `~~~` fences when counting H1s and placeholders, and resolves URL-encoded local image paths (`docs/images/My%20Shot.png`).
- `readme --bootstrap` rewrites only the template owner's `.github` CONTRIBUTING/SECURITY links in CONTRIBUTING.md; links to another org's or an upstream's guides stay as written.
- The social preview footer, the README nav line and the CI badge name the org's current login after an approved rename; `content social` renders the footer with the resolver its `--registry`/`--approved*` flags build. `content social --job` withholds the upload job (`needs-input:social-login`) when the rendered image names a different login than the slug it would be uploaded to.
- The Action no longer deletes a repository's own `assets/icon.png` after a rename, a transfer or an org rename. `action_prepare.py foreign` treats art as another repository's only on proof: a template's sidecar (`inputs.type: template`, or the template slug), or an output record whose `repository_id` differs from `$GITHUB_REPOSITORY_ID`. Otherwise it keeps the art and the icon and logs a notice, and the art regenerates under the new name. `meta` keeps `id` and `node_id`, and every sidecar output record carries `repository_id`.
- `fingerprint` reads the override `icon:` as the renderer does (YAML; a stdlib fallback strips quotes and a trailing comment), so changing an override icon whose line carries a comment regenerates the art.
- `.github/showcase.yml` `for: OWNER/REPO`, the checkout check (`--meta` with `--repo-dir`) and the `adopt` slug check compare the owner through the shared resolver (any case, any `former_slugs` login, CQ-03) and the repository name case-insensitively. A genuinely different repository is still refused.
- An owner spelled in another case (a lower-cased origin URL) takes the org's own spelling, so the README variant (`agent-skills` is A only in CompleteTech-Skills), the doctor R6 (AI-Ascension) and R9 rules, the nav line and the `describe` P1 rule (Pick-Your-AI) match. Former logins are not rewritten.
- `labels --plan` applies the `org labels` gates: a family on hold is refused (exit 2) unless `--allow-hold`, AI-Ascension gets only the `dependencies` create or patch, and `has_issues: false` repositories other than `.github`, archived repositories (`archived`) and the romgenie family answer `n/a`. `adopt` refuses a family on hold, also when called directly.
- Label writer job ids come from the operation (`…-label-<create|edit>-<name>[-to-<new>]-<hash8>` in `labels --plan` and `org labels`, the same parts in `adopt`), not its position, so a re-plan never queues one id with different content.
- Metadata whose fork `parent` is an `OWNER/REPO` string (the estate snapshot form) is normalized, so `topics`, `doctor` and `adopt` no longer crash on it. `meta --from-gh` captures `.github/showcase.yaml` too, and an override read from metadata is validated like a checkout's.
- Only watching-org forks are exempt from the icon, banner and footer (decisions 12, 13 and 18). The watching org's `.github` needs all three. Its other non-fork repositories are held (`hold:watching-non-fork`) until decided: `banner`, `card`, `content icon` and `readme` exit 2, and `--allow-hold` releases `banner`, `card` and `content icon`. `readme` has no `--allow-hold`: its hold message says the README stays unchanged while the repository is in the watching org instead of pointing to an option the command rejects. The Action treats a held or refused `readme` (exit 2 with a `hold` log or a `refused` result) like a held art family: a warning, the output skipped, the run green. Any other `readme` exit 2 (a `.github/showcase.yml` that fails its schema, a usage error) still fails the run. `footer --check README.md --org` with the watching org reads the README instead of answering `exempt`, since `--org` cannot tell its `.github` from a fork.
- `readme --mode header` (the Action's README step) keeps a tagline written for the repository when the repository has no description yet (`needs-input:description`), instead of emptying it; only an inherited tagline is emptied: the block still holds exactly a tagline of the template the repository was generated from, as it was then or as it is now (`meta --from-gh` now records `template_repository` and `template_taglines`), or, only when those are unknown, the template body is still pristine.
- `readme --bootstrap` (the template workflow's step before header mode, so every repository generated from the template runs it on each push) no longer erases a tagline written for the repository when it rebuilds the header with no description: the tagline block carries over and the header rule above decides it, in one place (`readme.tagline_body`), so only an inherited tagline is emptied. `readme --mode upgrade` (and `auto` when it picks upgrade) uses the same rule, so with no description it no longer fails with `readme-shrink` (exit 1, README unchanged): a tagline written for the repository is kept, and an inherited one is emptied without counting as a lost line. This holds in its additive preserve mode too (a README over 15000 bytes or on the org's `readme_preserve` list), where the tagline block now stays in place instead of being dropped. An unmarked bold tagline (a README adopted for the first time) is no longer erased silently (exit 0) with no description: when upgrade rebuilds the header (not in preserve mode), a single bare `**...**` line opening the README after its header lines (H1, badges, banner, `---`) moves into the tagline block by the same rule; a second bold line, one beside a tagline block that already holds a line, a bold line inside a centred `<div>`/`<p>` block, one in preserve mode, or one in an untouched template copy whose template taglines are unknown (where the rule would empty any line in the block on the next run) stays as authored text. `meta --from-gh` finds the template README's tagline block outside code, so a marker example in fenced or inline code is no longer read as the template's tagline (which also turned off the pristine-body fallback).
